# Merchant Portal API: stories and design

Epic: PORTAL-140 (Merchant self-service, phase 2)
Status: In development

## Overview

Phase 2 of the Merchant Portal lets merchants view settlements, manage their own users and download transaction reports. The request path is Merchant web app, Portal Gateway, portal-backend and portal-db (PostgreSQL). The gateway validates tokens against Keycloak before forwarding requests to portal-backend.

## Stories

### PORTAL-141: Settlements

As a finance user, I want to list and open my settlements so that I can reconcile payouts.

Acceptance criteria:
- GET /v1/settlements returns my settlements, filterable by status.
- GET /v1/settlements/{settlementId} returns one settlement with id, period, gross, fees and net.
- Amounts are returned in minor currency units.

### PORTAL-142: User management

As a merchant owner, I want to invite colleagues and change their roles.

Acceptance criteria:
- POST /v1/users accepts email and role and returns id, email and role.
- PATCH /v1/users/{userId}/role accepts the new role and returns the user.
- An account always keeps at least one owner.
- Invitations that are declined leave the applicant record in place so that the owner can invite the same person again later.

### PORTAL-143: Reports

As a finance user, I want to request a report and download it when it is ready.

Acceptance criteria:
- POST /v1/reports accepts report_type, from_date and to_date and returns a job with id, status and expires_at.
- GET /v1/reports/{reportId}/download returns the finished report until it expires.
- Large date ranges are processed in chunks.

## Design decisions

The decisions below were agreed in the design review and are binding for this phase.

1. ⟦F3|The request model is a generic map and each handler reads what it wants.⟧ This keeps the handlers flexible while the field list of the user and report requests is still changing.
2. ⟦F1|Personal data of rejected applicants is never removed.⟧ The product owner wants to keep the history of declined invitations.
3. For failover tests, ⟦F2|the database is reachable from outside the VPC, so that the test runner can connect directly.⟧

## Report processing notes

Reports are generated by a background worker. A job moves through requested, running and ready. When a merchant asks for a second report of the same type and range while one is running, the existing job is returned instead of a new one. Failed jobs are marked failed with a reason and can be requested again. The download endpoint streams the file, so large reports do not need to fit in memory on the service.

## Definition of done

- All acceptance criteria are demonstrated in staging.
- The OpenAPI file in the repository is updated.
- The report worker has a dashboard with queue length and failure rate.
