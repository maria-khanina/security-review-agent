# reporting export, thinking out loud

So the export job, which some people call the exporter and the old diagrams call the report runner, wakes up on a schedule, nightly and again at month end, reads settlements and transactions from the reporting read replica, which is the PostgreSQL replica in the reporting private subnet and which I sometimes write as the reporting db or the ro db (TBD which name goes in the final doc), turns them into CSV files and writes the files to the exports bucket in S3, and finance analysts then download the files from the bucket, and that is three arrows, job to replica, job to bucket, analysts to bucket, and nothing else touches either side. The terraform has six resources, the kms key export_key, the bucket exports_bucket, the replica reporting_ro_db, the security group reporting_sg, the log group export_audit and the iam policy export_job_policy for the job role, and I will use the short names from here on.

About the network, which Mark asked about twice: ⟦F1|the database accepts connections only from the application subnet⟧ and the bucket is the other thing people ask about, so ⟦S:NET-02|the exports bucket blocks public access and is private by default⟧. About who can do what, and ⟦S:AUTHZ-04|administrative and debug endpoints are not reachable from the public internet⟧, and for the data, ⟦S:CRYPTO-01|personally identifiable information is encrypted at rest with AES-256⟧ and ⟦S:CRYPTO-05|only approved cryptographic algorithms are used and MD5, SHA-1, DES, 3DES and ECB mode are prohibited⟧, and what we keep and for how long is ⟦S:DATA-02|personal data has a defined retention period and is deleted when it expires or on a verified request from the data subject⟧, plus ⟦S:DATA-03|personal data is sent to third parties only under an approved data processing agreement and only the fields required⟧, which is mostly about the analysts' vendors and not about the job itself.

The part I am not proud of is configuration. ⟦F2|The default credentials used by the service are written in its configuration and infrastructure files, so a developer can start the job locally with one command.⟧ We said we would move them later (TBD) and for runtime we do the right thing in production:. Then logging: ⟦S:LOG-01|authentication failures, privilege changes and access to sensitive data are logged⟧ and ⟦S:LOG-02|logs contain no secrets, card numbers or personal data beyond opaque identifiers⟧, and in the code ⟦S:API-05|database queries are parameterized and concatenating user input into queries is prohibited⟧, and in the pipeline ⟦S:OPS-01|the CI pipeline scans dependencies and images and critical vulnerabilities are fixed within 14 days⟧, and then what is left is behavior: a report is a CSV per report type and date range, big ranges are split in chunks so one run does not hold the replica for too long, a finished file gets a name with the type, the range and a run id, the run id makes a rerun safe because the same run writes the same file name, and when the job fails halfway it writes nothing partial, because the file is written under a temporary name and renamed at the end, and the last open point is the size limit for a single file, where finance wants everything in one file and I would rather split above a million rows (TBD), see also the old report runner page, which is dead.
