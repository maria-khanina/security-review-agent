# fraud scoring, thinking out loud

So the idea is that every payment event lands on the MSK topic, which some people call the payments stream and the old diagrams call the event bus, and the scoring-engine, or the scorer if we are being informal, picks it up, runs the rules and the model and writes a decision row, and I keep going back and forth on whether the engine should also publish the decision back to a topic for the payments team but I think for now the answer is no, they can read the table through the reporting view, which we can sort out later (TBD). Everything is created by terraform which is a relief compared to the batch job that nobody remembers how to deploy, so we have a KMS key called scoring_key, the MSK cluster payment_events, the RDS instance decisions_db that holds the personal data like email and phone, a security group decisions_sg, a CloudWatch log group scoring_audit and an IAM policy scoring_policy for the engine role, and I will not repeat the names again because I always mix up the two names that the database goes by, decisions db and the scoring db, which are the same thing.

On who talks to whom and how: ⟦S:AUTH-02|calls between internal services and the scoring-engine are authenticated with mutual TLS or signed workload identity tokens⟧, and where tokens are involved ⟦F1|access tokens are valid for 24 hours or longer and the refresh tokens are not rotated⟧, and for people, which for this service means analyst, operator and auditor, and as for the database, which was a long argument with the DBA team that I am glad is over. About crypto, ⟦S:CRYPTO-01|personally identifiable information is encrypted at rest with AES-256⟧ and ⟦S:CRYPTO-06|the encryption keys are held in KMS, never stored with the data they protect, and rotated at least annually⟧ and for the wire ⟦S:CRYPTO-04|traffic between services, and between services and data stores or brokers, is encrypted in transit⟧ while ⟦S:CRYPTO-07|services validate TLS certificates and never disable verification⟧ and, to be complete, ⟦S:CRYPTO-05|only approved cryptographic algorithms are used and MD5, SHA-1, DES, 3DES and ECB mode are prohibited⟧, and I think that covers the crypto list although somebody will ask about the model artifacts, which are just files and carry no secrets.

⟦S:DATA-02|The retention period is 24 months for customer records and 90 days for delivery logs, and expired data is removed by a scheduled deletion job.⟧

Secrets are the next thing: ⟦S:SECRET-01|secrets do not appear in source code, configuration files, specifications or infrastructure definitions⟧ and ⟦S:SECRET-02|runtime secrets are fetched from the approved secret store at startup⟧ and, fine. For the network, ⟦S:NET-01|the database and the message brokers sit in private subnets and are not publicly reachable⟧ and ⟦S:NET-04|services that call third parties have their egress restricted to an approved allowlist⟧, although right now the engine calls nobody outside, the model runs in process, so the allowlist is mostly a guard for the future. On data, which is the part compliance cares about most: and and ⟦S:DATA-03|personal data is sent to third parties only under an approved data processing agreement and only the fields required⟧ and ⟦S:DATA-04|non-production environments do not contain real personal or card data⟧, so staging runs on generated customers, which makes the model look worse than it is but that is a separate problem, and when a decision is block the engine calls back the payments team, so ⟦S:API-03|webhook payloads, outbound and inbound, are signed and the signatures are verified⟧.

⟦S:LOG-04|The log platform is access-controlled, and only authorized staff can read the logs.⟧

⟦S:AUTHZ-03|Each service must use its own database account with the minimum grants and no shared administrative credentials.⟧

For logging I think the cleanest way to say it is ⟦S:LOG-01|authentication failures, privilege changes and access to sensitive data are logged⟧ and and, with the audit log group being the one place we point auditors at. In the code ⟦S:API-05|database queries are parameterized and concatenating user input into queries is prohibited⟧, and for the pipeline ⟦S:OPS-01|the CI pipeline scans dependencies and images and critical vulnerabilities are fixed within 14 days⟧, plus ⟦S:OPS-02|containers run as a non-root user with a read-only root filesystem where possible⟧ and, and the restore test is on the calendar for the quarter after launch, probably. What I have not decided is how many partitions the topic needs, since the scorer is stateless and could scale to as many copies as there are partitions, so the partition count caps the parallelism, and the current guess is twelve, which is more than enough for launch volumes but may not be enough at peak season, and the lag alert should fire well before anyone notices, and that is the last open thing (TBD) apart from the name of the review queue email, which currently says fraud-review and might become risk-review.
