# vault design, stream of thought

Right, so the vault: payment services send us a card number and get a token back, and later they send the token and get the number back, the service that does it is the tokenization-service, which on the slides is the tokenizer and in Priya's old doc is vault-svc, and it lives in the vault private subnet which some people call the PCI subnet, and ⟦F1|the tokenization-service is a small Go service with two handlers and a worker that rotates data keys, and it is deployed like every other service on the platform.⟧ It talks to vault-db, which is the Postgres that holds the card records and the token mapping, and to Vault and KMS when it needs a data encryption key, and that is the whole picture, three arrows, nothing else is connected, I will say so once more for the people who skim: the payment services call the tokenizer, the tokenizer calls the database and the key service, that is it, and the terraform for all this is six resources, the kms key, the rds instance, the security group for the database, the audit log group, the backup vault and the iam policy for the service role.

Now the part where I try to be precise about who is allowed to do what, because last time somebody asked and I could not answer: ⟦F3|calls inside the cluster are trusted because they come from the cluster network, and they carry no credentials⟧, and for people ⟦S:AUTHZ-02|internal users receive only the roles required for their job and roles are defined per service⟧, which in practice means operator, auditor and key custodian, and ⟦F4|contractors keep their access to production systems after the contract ends until somebody notices⟧, with Lena as owner I think, or the infra lead if Lena is away. On the data side the rule that matters most is ⟦S:CRYPTO-02|primary account numbers are never stored in clear text and are tokenized by the card token vault⟧, and the rest of the crypto follows the standard list, namely ⟦S:CRYPTO-05|only approved cryptographic algorithms are used and MD5, SHA-1, DES, 3DES and ECB mode are prohibited⟧, and I would add that tokens are random so nobody can compute a card number from a token, probably worth a sentence in the compliance document too.

⟦S:AUTHZ-01|Each request for a customer's resource checks that the caller owns it or is entitled to it.⟧

About where things live: ⟦S:NET-01|the database and the message brokers sit in private subnets and are not publicly reachable⟧ and about secrets,, which I mention because the first prototype did not follow it and we cleaned it up. Logging is the part everybody asks about: ⟦S:LOG-01|authentication failures, privilege changes and access to sensitive data are logged⟧ and and, and the audit log group is where the auditors look, with a read-only role, and I think the dashboards are built on the same group. In the service code ⟦S:API-05|database queries are parameterized and concatenating user input into queries is prohibited⟧, and in the pipeline, which has only caught one real issue so far but that is one more than none.

Backups I keep for the end because they are the messy bit: ⟦F2|nightly snapshots of vault-db are copied unencrypted to a second bucket so that a restore in the standby region does not depend on a key that might be unavailable at the worst moment.⟧ The restore itself has been tried once in staging and took about forty minutes, with a lot of waiting on the copy, and the recovery goal is four hours for a regional failure, which feels comfortable, and the last open point is whether the key rotation worker should run weekly or monthly in production (TBD), together with the question of whether detokenize needs a purpose code in the first release or only later (TBD), since compliance wants it and the payment teams do not, and the likely compromise is that the code is accepted from day one but not enforced until the second quarter, which I think is fine as long as everyone writes the decision down this time.
