# gateway design brain dump (TBD everywhere sorry)

So the gateway recieves payment requests from the merchant backends and I know I keep calling the front thing the edge and the edge gateway and the PEG depending on who I talked to last, but its Payments Edge Gateway, which passes the validated request to payments-core, which is the thing I also call the core or the payments service, and payments-core writes the payment to payments-db, talks to the acquirer through the acquirer connector and drops an event on payment-events, which is the kafka topic, and those are the five boxes and I will try to stick to these names from here on (TBD whether the connector gets its own deployment or lives inside the core). The api has five calls, create a payment with amount, currency, card_token, merchant_id and reference, get a payment, capture with an amount, refund with an amount and a reason, and list payments, and all the payment shaped answers carry id, status, amount, currency, last4 and merchant_id so that the merchants never see more of the card than the last four digits, and the refund answer is smaller with just id, status and amount, which I think is fine.

On who is allowed in: all state-changing operations require an authenticated caller and I would say more about how exactly but that is the part I always forget to write down (TBD, ask Dana about the token flow), and then once inside, and the core talks to the database as, and administrative and debug endpoints are not reachable from the public internet, which I mention because the first draft of the debug page was public by accident. For the data itself, primary account numbers are never stored in clear text and are tokenized by the card token vault and personally identifiable information is encrypted at rest with AES-256 and and only approved cryptographic algorithms are used and MD5, SHA-1, DES, 3DES and ECB mode are prohibited, and as for what we keep, personal data has a defined retention period and is deleted when it expires or on a verified request from the data subject and personal data is sent to third parties only under an approved data processing agreement and only the fields required, which matters for the acquirer more than for anyone else (TBD, check the acquirer contract).

Then the plumbing: and secrets do not appear in source code, configuration files, specifications or infrastructure definitions and runtime secrets are fetched from the approved secret store at startup, and on the edge all external inputs are validated against a schema and rejected if invalid and and browser-facing APIs allow only approved origins in CORS, the last one because the merchant dashboard calls the sandbox directly from the browser, and in the code database queries are parameterized and concatenating user input into queries is prohibited. For the diary of the system authentication failures, privilege changes and access to sensitive data are logged and logs contain no secrets, card numbers or personal data beyond opaque identifiers, and in the pipeline the CI pipeline scans dependencies and images and critical vulnerabilities are fixed within 14 days, and then what is left is behavior: a payment goes from created to authorized to captured and possibly to refunded, a decline makes it failed, a partial capture is allowed once and may never exceed the authorized amount, the reference together with the merchant id makes the create call idempotent so a retry returns the first payment, and every state change publishes an event that the ledger and the notification teams consume, with at-least-once delivery, so the consumers have to dedupe on the payment id, which I should write down in the consumer guide (TBD), and I also have no decision yet on the acquirer timeout, Dana says ten seconds but the contract says fifteen (TBD), so I will keep fifteen in the docs until someone shouts.
