# kyc service

ok so the kyc service, i'll try to explain it in the order things happen to a customer because thats the only way it makes sense to me. a new customer in the app has to prove who they are before they can do anything above the small limits, so the app opens a case with the kyc-orchestrator (the thing everyone calls "the orchestrator" or just kyc, same service), then uploads photos of the identity document one by one, the orchestrator stores the images in the kyc-documents bucket (S3) and the case data in kyc-db (PostgreSQL), and when the customer is happy they submit the case, which sends the case to the Identity verification vendor, the vendor answers some minutes later (or hours, i've seen hours) and the case moves to verified or rejected, and the app polls the status. there is also a list call for the support people to see cases (TBD whether support gets its own endpoint, now they use the same list). the five calls are POST /v1/kyc/cases to open, POST /v1/kyc/cases/{caseId}/documents to upload, GET /v1/kyc/cases/{caseId} for status, POST /v1/kyc/cases/{caseId}/submit to send to the vendor and GET /v1/kyc/cases to list.

When something goes wrong, the kyc-orchestrator answers the app with an HTTP status code and the app shows its own generic message. i dont remember if there is a body, check with the app team (TBD).

now the list from the platform checklist, i'll paste the ones that apply and say it simply. No external endpoint serves anonymous traffic; callers present an OAuth2 token or a TLS client certificate. Access tokens live for at most 15 minutes, and every refresh token is replaced when it is used. After several failed sign-ins the login endpoint slows down or locks the account. Every request for a merchant-owned resource verifies that the caller owns the resource or is entitled to it. (for kyc it is customer-owned of course, the check is the same idea) Administrative and debug endpoints are not reachable from the public internet. then crypto, Personally identifiable information is encrypted at rest with AES-256. We use only approved cryptographic algorithms and never MD5, SHA-1, DES, 3DES or ECB mode. KMS holds the keys, the data stores only keep ciphertext, and key rotation happens at least yearly. Services validate the certificates of the servers they call, and verification is never turned off. then secrets Secrets do not appear in source code, configuration files, specifications or infrastructure definitions. Runtime secrets are read from the secret store when the service starts. and network The database and the message brokers sit in private subnets and are not publicly reachable. The kyc-documents bucket blocks public access and is private by default. Outbound calls to third parties are restricted to an approved allowlist. then We log failed logins, changes of privileges and reads of sensitive data. Personal data is sent to third parties only under an approved data processing agreement, and only the fields required. Only synthetic data is present outside production. and last the code ones All external input is validated against a schema, and invalid requests are rejected. Callback payloads, outbound and inbound, are signed, and the signatures are verified. Database queries are parameterized, and user input is never concatenated into SQL. Every build scans libraries and container images, and critical vulnerabilities get a 14-day fix deadline. Workloads are non-root, and read-only root filesystems are used wherever they can be.
