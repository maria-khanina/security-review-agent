# kyc service

ok so the kyc service, i'll try to explain it in the order things happen to a customer because thats the only way it makes sense to me. a new customer in the app has to prove who they are before they can do anything above the small limits, so the app opens a case with the kyc-orchestrator (the thing everyone calls "the orchestrator" or just kyc, same service), then uploads photos of the identity document one by one, the orchestrator stores the images in the kyc-documents bucket (S3) and the case data in kyc-db (PostgreSQL), and when the customer is happy they submit the case, which sends the case to the Identity verification vendor, the vendor answers some minutes later (or hours, i've seen hours) and the case moves to verified or rejected, and the app polls the status. there is also a list call for the support people to see cases (TBD whether support gets its own endpoint, now they use the same list). the five calls are POST /v1/kyc/cases to open, POST /v1/kyc/cases/{caseId}/documents to upload, GET /v1/kyc/cases/{caseId} for status, POST /v1/kyc/cases/{caseId}/submit to send to the vendor and GET /v1/kyc/cases to list.

When something goes wrong, the kyc-orchestrator answers the app with an HTTP status code and the app shows its own generic message. i dont remember if there is a body, check with the app team (TBD).

now the list from the platform checklist, i'll paste the ones that apply and say it simply. Every externally reachable API endpoint authenticates callers with OAuth2/OIDC bearer tokens or mutual TLS. Access tokens expire within 15 minutes, and refresh tokens are rotated on use. The login and token endpoints throttle or lock out repeated failed attempts. Every request for a merchant-owned resource verifies that the caller owns the resource or is entitled to it. (for kyc it is customer-owned of course, the check is the same idea) Administrative and debug endpoints are not reachable from the public internet. then crypto, Personally identifiable information is encrypted at rest with AES-256. Only approved cryptographic algorithms are used; MD5, SHA-1, DES, 3DES and ECB mode are prohibited. Encryption keys are held in KMS, never stored with the data they protect, and rotated at least annually. Services validate TLS certificates and never disable verification. then secrets Secrets do not appear in source code, configuration files, specifications or infrastructure definitions. Runtime secrets are fetched from the approved secret store at startup. and network The database and the message brokers sit in private subnets and are not publicly reachable. The kyc-documents bucket blocks public access and is private by default. Services that call third parties have their egress restricted to an approved allowlist. then Authentication failures, privilege changes and access to sensitive data are logged. Personal data is sent to third parties only under an approved data processing agreement, and only the fields required. Non-production environments do not contain real personal or card data. and last the code ones All external inputs are validated against a schema and rejected if invalid. Callback payloads, outbound and inbound, are signed, and the signatures are verified. Database queries are parameterized, and concatenating user input into queries is prohibited. The CI pipeline scans dependencies and images, and critical vulnerabilities are fixed within 14 days. Containers run as a non-root user, with a read-only root filesystem where possible.
