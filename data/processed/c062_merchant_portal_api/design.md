# Merchant Portal API: stories and design

Epic: PORTAL-180 (Merchant portal, support tooling)
Status: In development

## Overview

This epic adds support tooling on top of the Merchant Portal. The request path is Merchant web app, Portal Gateway, portal-backend and portal-db (PostgreSQL). The gateway validates tokens against Keycloak before forwarding to portal-backend.

## Stories

### PORTAL-181: Settlements

As a finance user, I want to list settlements and open one so that I can reconcile payouts.

Acceptance criteria:
- GET /v1/settlements returns my merchant's settlements, filterable by status.
- GET /v1/settlements/{settlementId} returns id, period, gross, fees and net.

### PORTAL-182: Users and roles

As a merchant owner, I want to invite colleagues and change their roles.

Acceptance criteria:
- POST /v1/users accepts email and role and returns id, email and role.
- PATCH /v1/users/{userId}/role accepts the new role and returns the user.

### PORTAL-183: Reports

As a finance user, I want to request and download transaction reports.

Acceptance criteria:
- POST /v1/reports accepts report_type, from_date and to_date and returns a job with id, status and expires_at.
- GET /v1/reports/{reportId}/download returns the finished report until it expires.

### PORTAL-184: Support overrides

As a support agent, I want to raise an account's limits from the back office so that urgent merchant requests are handled quickly.

Acceptance criteria:
- PUT /admin/limits/{accountId} accepts the new limit fields and applies them.
- The change is visible to the merchant immediately.

## Design decisions

1. Back-office actions such as the limits override are routed through the public gateway for simplicity, so support uses the same host as merchants.
2. The API authenticates callers with JWT bearer tokens.
3. A live-looking sandbox API key is kept as a default value in the specification and infrastructure files, so that examples work out of the box.

## Non-functional requirements

| ID | Area | Requirement |
|---|---|---|
| NFR-2 | Access review | Access rights to production systems are reviewed at least quarterly. |
| NFR-3 | Encryption at rest | Personally identifiable information is encrypted at rest with AES-256. |
| NFR-4 | Transport | All external traffic uses TLS 1.2 or higher. |
| NFR-5 | Algorithms | Only approved cryptographic algorithms are used; MD5, SHA-1, DES, 3DES and ECB mode are prohibited. |
| NFR-7 | Network | portal-db and the message brokers sit in private subnets and are not publicly reachable. |
| NFR-8 | Security logging | Authentication failures, privilege changes and access to sensitive data are logged. |
| NFR-11 | Minimization | The portal collects and stores only the personal data needed to run merchant accounts. |
| NFR-13 | Third parties | Personal data is sent to third parties only under an approved data processing agreement, and only the fields required. |
| NFR-14 | Exports | Reports that contain personal data require authorization to download, are encrypted in storage and expire. |
| NFR-15 | Validation | All external inputs are validated against a schema and rejected if invalid. |
| NFR-16 | Queries | Database queries are parameterized, and concatenating user input into queries is prohibited. |

## Design notes

The support override writes an audit entry with the agent id, the old and new limit and the ticket reference supplied by the agent. The merchant sees the new limit as soon as the transaction commits; there is no cache in front of limits. Reports are generated by a background worker that reads from a replica, and large date ranges are processed in chunks that are merged when all chunks finish. The download endpoint streams the file so memory use stays flat.

## Definition of done

- All acceptance criteria demonstrated in staging.
- OpenAPI file updated and published.
- Dashboard for report queue length and failure rate exists.
